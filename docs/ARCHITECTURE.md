# 架构说明

```text
┌──────────────────────────────────────────┐
│ 微信原生小程序                           │
│ 登录 / 地图 / 车队 / PTT UI / 位置采集   │
└───────────────┬──────────────────────────┘
                │ HTTPS + WebSocket
┌───────────────▼──────────────────────────┐
│ Spring Boot API（当前为模块化单体）       │
│ Auth / Team / Location / Floor / RTC票据  │
└───────────┬───────────────────┬──────────┘
            │                   │
      PostgreSQL/PostGIS      Redis
      用户/车队/轨迹          在线位置/麦权/会话
            │                   │
            └─────────┬─────────┘
                      │
              TRTC（后续接入）
```

## 为什么首期不拆微服务

MVP 的核心风险不是单机吞吐量，而是产品交互、平台权限、真机后台行为与实车音质。先做模块化单体可以：

- 保持部署和排障简单；
- 让车队、位置、麦权事务边界清楚；
- 等到真实并发与成本数据出现后再拆分；
- 避免为了“架构好看”提前引入消息队列和分布式一致性。

## 实时通道

### HTTPS

用于登录、创建 / 加入车队、获取房间快照、附近查询和 RTC Ticket。

### WebSocket

用于：

- 队员加入 / 离开；
- 精确位置更新；
- 抢麦请求与释放；
- 心跳和连接状态；
- 后续掉队提醒、队长广播。

### RTC

只负责音频媒体传输。麦权由 MotoLink 服务端决定，不能仅依赖客户端静音按钮，否则多端竞争时会串麦。

## 数据隐私原则

- 附近陌生人：只返回距离及模糊坐标；
- 同队骑行：在用户主动加入并开启共享后才广播精确坐标；
- 位置设置短时有效期，过期不展示在线；
- 服务端日志避免记录原始精确经纬度；
- 生产环境需要用户可撤回授权、删除轨迹和注销账号。
