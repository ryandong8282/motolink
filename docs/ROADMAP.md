# 路线图

## M0：当前骨架

- 小程序主要页面；
- 开发态登录；
- 内存版车队、位置和麦权；
- WebSocket 协议；
- Mock RTC；
- 单元测试和 CI。

## M1：真机语音 POC

- 企业小程序权限验证；
- 服务端 TRTC UserSig；
- `trtc-wx` 接入；
- 前台半双工语音；
- 网络切换与异常退出测试；
- 路测数据记录。

## M2：可用的封闭测试版

- 微信登录 + 手机号绑定；
- PostgreSQL 用户 / 车队持久化；
- Redis 麦权与在线位置；
- 轨迹本地缓存及批量上传；
- 队长权限、踢人、解散；
- 基础举报和拉黑；
- 监控、日志脱敏、限流。

## M3：商用准备

- 隐私授权与数据删除；
- 内容审核；
- 管理后台；
- 生产高可用和备份；
- 安全测试；
- 备案 / 上架材料；
- 真实机型矩阵验收。

## 是否转原生 APP 的决策点

完成 M1 后，根据真实测试决定：

- 小程序前台对讲是否足够满足目标用户；
- 锁屏 / 蓝牙按键是否成为刚需；
- 后台定位和微信宿主限制是否影响核心体验；
- 用户是否愿意安装独立 APP。

若锁屏对讲、系统级唤醒、头盔物理按键成为硬性要求，应转为 Flutter 业务层 + Swift/Kotlin 原生 RidingCore，而不是继续给小程序打补丁。
